The Challenge 
You are tasked with designing and building a Facility Patient Billing Module for eFiche. The module must handle: 
1. Visit-based billing where a single visit can have multiple line items (lab tests, consultations, medications) 
2. Multi-cashier concurrency, two cashiers at the same facility may attempt to process payments against the same invoice simultaneously 
3. Insurance coverage that is configured per-facility, not globally 
      4. Mobile money payment confirmation that arrives asynchronously via webhook (seconds to minutes after initiation) 
5. Partial offline functionality, the system must remain usable when internet connectivity is intermittent
Deliverables 
1. Code Review, Critique the Provided Snippets (written, ~500 words) 
Review all three code snippets above and answer: 
a) The race condition. Identify the exact race condition in processPayment. Under what scenario does it produce incorrect data? Write the corrected version using PostgreSQL-level locking. Explain why application-level checks alone are insufficient here. 
b) The webhook idempotency bug. The deduplication check in handleEfichePayWebhook has a critical flaw that will cause duplicate payments under realistic conditions. Identify it precisely. Explain what happens when a webhook is delivered twice within 50 milliseconds. Propose a fix that is atomic. (Hint: think about what the model's $fillable array has to do with this.) 
Critique of InvoiceController.php: processPayment
The current implementation of processPayment suffers from a "check-then-act" race condition. When two cashiers process payments for the same invoice simultaneously, both may read the same $remaining balance before either has created a payment record. This allows both requests to pass the validation check, resulting in a total payment that exceeds the invoice amount. To fix this, PostgreSQL-level row locking (FOR UPDATE) should be used on the invoice record within a database transaction to ensure only one process can calculate and update the balance at a time.
Critique of WebhookController.php: handleEfichePayWebhook
The idempotency check in handleEfichePayWebhook is non-atomic. If two identical webhook notifications arrive within milliseconds, both might find that $existing is null and proceed to create duplicate payment records. The fix requires a unique database constraint on event_id and ensuring the event_id is included in the model's $fillable array. Utilizing an atomic updateOrCreate or handling the database exception on duplicate insertion ensures true idempotency.
Critique of BillingPage.tsx
The use of a hardcoded COVERED_INSURANCES array is a "Hardcoded Configuration" anti-pattern. This makes the system rigid and requires a code deployment every time a facility changes its insurance partnerships. In a multi-facility environment, this configuration must reside in the database, associated with each specific facility. The frontend should consume this via a filtered API endpoint, allowing for dynamic updates without redeploying the application.
c) The insurance hardcode. The COVERED_INSURANCES = [1, 3, 5, 7, 9] pattern is a symptom of an architectural decision, not just a lazy line of code. Name the pattern. Explain what category of production incident this causes (give a concrete scenario). Then describe the correct data model: where should this configuration live, who owns it, and how should the frontend consume it?

3. Working Prototype

Backend (Laravel):

Frontend (Next.js + TypeScript):

- Shows invoice line items and remaining balance

You do not need to integrate with the real eFichePay API. A stub or mock is acceptable, but the webhook handler must be real and must be testable by calling it directly.
